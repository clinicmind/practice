# 審核工作台

在瀏覽器快速審核一個階段（或一個模組）的內容。英文和繁中左右對照，每項按「同意」或「要修改」，最後把決定複製給 Claude。

工作台只是輔助。**自動預檢標記是提示，不取代臨床判斷。** 登記 `content/REVIEW.md` 的規則不變：要有擁有人在對話中的明確同意。

## 給擁有人：三步用法

1. **請 Claude 產生工作台，然後取得檔案。** 例如說「請產生 EFT 的審核工作台」。你會拿到一個檔案，名稱像 `eft.html`。這個檔案不用上網、不用安裝，下載後雙擊就能用瀏覽器開。（手機和電腦都可以。）
2. **逐項審。** 每一項左邊是英文，右邊是繁中（手機上改為上下排列）。
   - 按「**同意**」：這一項可以。
   - 按「**要修改**」：這一項要改。在旁邊的框寫一句話，說哪裡要改。
   - 按錯了，再按一次同一個按鈕，就取消。
   - 頂部有一行摘要：「要你判斷的 N 項；自動預檢警告 M 項；其餘是說明」。
   - **橘色粗框「預審留給你判斷」**：預審報告把這一項留給你（沒處理、請你決定、建議）。要看。
   - **橘色 ⚠**：電腦自動預檢的警告（禁用字詞、句數、中英不一致）。
   - **灰色、收合的「預審已修正或只是說明」**：預審報告提到這一項，但說已修正，或只是說明。想看再展開。
   - 沒有標記不代表沒問題。
   - 頂部的「已看 x／全部 y」是進度。「只看有預檢標記的」「只看還沒決定的」可以縮短清單。
   - 你的決定會自動存在這個瀏覽器，關掉再開還在。換瀏覽器或換電腦不會跟著走。
3. **按頂部的「複製決定」，到 Claude 的對話框按貼上，送出。** 想分模組送，就按每個模組卡片上的「複製這個模組的決定」。沒有看到「已複製」時，頁面會顯示一個選好的文字框，按 Ctrl+C（Mac 是 ⌘+C）複製就好。

## 給 Claude：收到決定後怎麼處理

### 複製出來的 JSON

單一模組：

```json
{ "stage": "eft", "module": "eft-attunement", "version": "1.0.0",
  "decisions": [ { "id": "eft-attunement-e02", "status": "revise", "note": "標準 2 沒有試探詞" } ] }
```

按頂部「複製決定」且工作台有多個模組時，貼出來的是這種物件的**陣列**。

- `status` 只有 `agree`（同意）和 `revise`（要修改）。沒按的項目**不會出現**，視為還沒看。
- `id`：模組本身是 `<slug>`；簡介是 `<slug>-intro`；題目、走讀決策點、反思題用內容裡的 id（沒有以 slug 開頭的 id，會補上 slug 或會談 id）。
- `version` 是工作台產生時模組的 `version`。

### 處理步驟

1. **先核對範圍。** 比對 `module`／`version` 和 `content/.../module.yaml`。版本不一樣就停下來，告訴擁有人這份決定是舊版的。
2. **算出每個模組的狀態**：
   - 「全部同意」＝模組本身和簡介、每一個題目、決策點、反思題都有決定，而且全部是 `agree`。內容有哪些 id 以工作台頁面為準（頁面內嵌的 `wb-data` 有完整清單）。
   - 有任何 `revise`，或有項目沒決定，就不算全部同意。
3. **全部同意的模組**：不要直接登記。**在對話中請擁有人確認**（例如：「`eft-attunement` 英文和繁中共 43 項都同意。要登記到 `content/REVIEW.md` 嗎？」）。得到明確同意後，才在 `content/REVIEW.md` 加 `slug｜locale｜version｜日期`，英文和繁中各一列；有關門檻的細節看 `docs/HANDOFF.md`（例如 EFT 登記前要先套用 `0004_cohort_stages.sql`）。
4. **有「要修改」的項目**：把每一項的 `id` 和 `note` 整理成清單，交給子 session 修改（只改被標記的項目，英文和繁中同步）。修改會讓 `version` 變動的話，要先取得擁有人同意（見 `CLAUDE.md`）。
5. **改完後產生新的工作台**，請擁有人重審被改過的項目：
   `npm run review:workbench -- --stage <階段> --module <模組>`
   版本沒變時，擁有人先前的決定還在她的瀏覽器裡；要重審的項目她可以按「要修改」再按一次取消，或直接改成「同意」。
6. 回報給擁有人：哪些模組全部同意、哪些要改、哪些還沒看完。

## 產生指令

```
npm run review:workbench -- --stage eft                         # 整個階段
npm run review:workbench -- --stage eft --module eft-attunement # 單一模組
```

輸出在 `review/<階段>[-<模組>].html`。`review/` 已列入 `.gitignore`，不會進 repo。

## 預檢規則

| 標記 | 規則 | 維護 |
|---|---|---|
| 禁用字詞 | 診斷名稱、藥物名稱、有版權量表（中英）。命中的字會用底色標出 | `scripts/review-forbidden-terms.ts`：在清單加一行字串。英文要整個字詞符合；全大寫縮寫（如 `DID`）分大小寫；中文不要放太短的詞 |
| 示範回應句數 | 題目的情境或標準寫了「一至兩句」「one or two sentences」之類，而示範回應的句數超過 | `scripts/review-precheck.ts` 的 `maxSentencesRequested` |
| 中英結構不一致 | 示範回應句數差 2 句以上、問句只出現在一種語言、決策點類型／選項 id／`fit` 不同、題目或會談數量不同 | 同上（`compareDrill`、`compareDecision`） |
| 預審報告提到 | `docs/reviews/*.md` 提到這個 id（完整 id、`e02` 這種簡寫、`h01–h05` 範圍、`s1-d3`、「模組 N」「M N」）。展開可看報告原文和行號 | `parseReportRefs`。報告要在標題用反引號寫出模組 slug，簡寫才認得出屬於哪個模組 |

### 預審報告提到的項目怎樣分類

每一行報告分成三種（`parseReportRefs` 的 `status`）：

- **留給你判斷（醒目）**：在「沒有處理」「需要擁有人判斷」之類的標題下；或那一行有「沒有改」「請擁有人」「待確認」「建議」「是否」等字；或在報告摘要裡、而摘要那一點沒有寫「已處理」，也沒有在後面的「已處理」節（標題「摘要第 N 點」或「處理摘要第 1–3 點」）被處理。
- **已處理（灰色、收合）**：在「已處理」「已修正」「已完成」的段落裡（除非那一行還有請擁有人看的字）；或那一行寫「已修正」「已改」「已補」等。摘要裡寫了「已處理」的那一點也算。
- **說明（灰色、收合）**：只是提到，沒有說已處理，也沒有要你判斷（例如「符合標準」）。

判斷靠關鍵字，會有誤分。灰色那一邊多收了一則，頂多是漏標；想核對就展開「預審已修正或只是說明」。報告想讓某一項醒目，就在那一行寫「請擁有人確認」。

### 句數規則的已知限制

- 句數用標點符號數。夾在句子中間的引文（例如：你聽到「笨。又來了。」然後……）裡的句號、問號不算句尾。引文放在句首，或引文後面接空白加大寫字，照舊算句尾。中文「說「好。」他走了」會少算一句。
- 「寫一句回應」的「句」是「一個」，不是句數上限（英文是 one response）。「一句話」「兩句短句」才是句數。
- 評分標準裡「in one sentence, before it says…」「先用一句話回應……再說……」只是規定其中一部分，不算整個回應的上限。題目情境（context）寫的「寫一句話」才是上限。
- 英文「in the middle of a sentence」這種描述不算上限。
- 問句比對（中英結構）不看引號裡的問句。
