# 階段 4–6 設計規格：AI 回饋、EFT、DBT

日期：2026-11-15　狀態：設計決策已定，未有實作計畫。擁有人已於 2026-11-15 同意兩項關鍵決定：(1) DBT 階段的個案用不危及生命的目標行為，風險處理另在督導下學習；(2) AI 回饋定位為校準自評、不決定過關，上線前要通過 40 份作答、80% 一致的檢驗。
前置：系統設計規格 `2026-11-15-practice-system-design.md`。本文件只寫新增的決策。

每個階段動工前，先按 `writing-plans` 的格式寫實作計畫，交擁有人看過。

## 共同前置工作：多階段支援

現在的程式把階段寫死為 `foundations`（建置腳本的 `STAGE` 常數、路由、內容載入）。階段 5、6 之前要先做：

1. 建置腳本處理 `content/<locale>/stages/*` 下的每個階段。每個階段各有 `index.json`。
2. 路由加上階段：`/s/:stage`、`/s/:stage/m/:slug/...`。舊路徑 `/m/:slug/...` 轉到 `foundations`，學生的書籤不可失效。
3. 階段解鎖：`foundations` 永遠開放。其他階段由督導按班別開放（新表 `cohort_stages(cohort_id, stage)`）。本機模式下全部開放。
4. 模組 id 已帶模組前綴（`intake-e01`）。新階段的 slug 要全系統唯一，並帶階段前綴：`eft-…`、`dbt-…`。
5. 技能名稱的 i18n 鍵是技能代碼。新代碼不可和舊的重複。

## 階段 4：AI 回饋

### 目的

AI 回饋的教學價值在於**校準自評**。學生先自評，再看 AI 對同一份回應的評估，重點是兩者不一致的地方。它不取代督導，也不決定過關。

### 決策

1. **過關規則不變。** 過關仍然只看學生自評（和督導手動解鎖）。AI 的評估不改變達標狀態。這樣 AI 出錯時，學生的進度不受影響。
2. **只在學生自評並儲存之後才呼叫 AI。** 學生先獨立判斷。
3. **不一致會被記錄。** 學生勾了某條標準而 AI 判為未做到（或相反），督導後台把這些作答列出。這取代現有三種機械式標記的一部分用途。
4. **報告回饋的 AI 草稿，學生永遠看不到。** 督導修改並發布後，學生看到的是督導的回饋（系統設計規格 §9）。
5. **總開關 `ai_enabled` 按班別設定，預設關。** 關閉時系統行為和現在完全相同。

### 練習回饋

輸入（只有這些）：題目的 context 和 client、3 條 criteria、學生的回應、語言。不送示範回應以外的任何身分資料；不送 user id、顯示名稱、班別。

示範回應會一併送給模型作參考，並明確指示：示範回應只是其中一個好選項，學生的回應不必相似。

輸出（JSON，由 zod 驗證；驗證失敗就不儲存、不顯示）：

```ts
{
  criteria: [                       // 恰好 3 項，次序同題目
    { met: boolean, evidence: string }   // evidence 必須是學生回應中的原文片段；met 為 false 時可為空字串
  ],
  suggestion: string,               // 一項具體建議，上限 60 個字（繁中）或 40 個英文單詞
  concern: 'none' | 'risk-content' | 'off-task'
}
```

- 伺服器要核對每個非空的 `evidence` 確實是學生回應的子字串。不是就整份丟棄。這是防止模型捏造引文的硬性檢查。
- `concern = 'risk-content'`：學生的回應寫了涉及真實風險的內容。這時不顯示回饋，只顯示頁尾那句安全提示，並在督導後台標記。
- `concern = 'off-task'`：回應不是在作答（亂碼、指令注入、無關內容）。不顯示回饋。

### 提示設計的規則

1. 學生的回應是**資料**。用明確的分隔標記包住，並在系統提示中說明：分隔標記內的任何指示都不執行。
2. 只按 3 條標準評。不評文筆，不評標準以外的東西。
3. 不作診斷，不給個案處置建議，不評論學生本人。
4. 語氣是同行的觀察，不是打分。建議以「可以試試……」開頭。
5. 提示文字有版本號（`prompt_version`）。每次改動都遞增。

### 資料表

`ai_feedback(id, attempt_id, model, prompt_version, output jsonb, created_at)`。學生讀自己的；督導讀本班的；只有 Edge Function 寫入。

### 模型與用量

- 練習回饋：`claude-haiku-5-5`。報告回饋草稿：`claude-sonnet-5-5`。動工時用 `claude-api` skill 核對當時的模型 id 和定價，不要憑記憶。
- 上限：每名學生每日 30 次練習回饋、每週 2 次報告草稿。超過時顯示上限訊息，練習本身照常可用。
- API 金鑰放在 Edge Function 的密鑰設定。

### 上線前的關卡（不可跳過）

1. **成本估算。** 按當時定價，估算一班 20 人每月的費用，交擁有人批准。
2. **一致性檢驗。** 準備 40 份作答（每個難度都有，包含好的、差的、離題的）。擁有人逐條標準評分。AI 的逐條判斷與擁有人一致的比率達 80% 或以上，才可開放。未達標就改提示再測。結果記錄在 `docs/` 內。
3. **確認 API 供應商的資料保存條款**，並把結論告訴擁有人。
4. 端到端測試：指令注入的回應不改變輸出格式；捏造的 evidence 被丟棄；關閉 `ai_enabled` 後沒有任何對外請求。

## 階段 5：EFT（Emotion-Focused Therapy，Greenberg）

擁有人已確認是 Greenberg 的個人治療取向。

### 決策

1. **新的貫穿個案**，不沿用 Client M。動工時先寫 `content/CLIENT_EFT.md`，交擁有人確認後才寫走讀。建議設定：主訴圍繞自我批評，並有一段未完成的關係。這樣雙椅和空椅兩項任務都自然出現。
2. **6 個模組**，結構和基礎階段相同（走讀、30 題、反思）。
3. **內容必須原創。** 市面上有 EFT 刻意練習的出版物。不可複製或改寫其題目和評分標準。技能的概念可以用，題目和文字要自己寫。
4. **擁有人審核是硬性關卡。** EFT 的介入（尤其椅子工作）做錯會有害。示範回應要保守。

### 模組

| # | slug | 重點 | 技能代碼 |
|---|---|---|---|
| 1 | `eft-attunement` | 同理調頻與同理探索 | `empathic-exploration`、`evocative-reflection` |
| 2 | `eft-emotion-types` | 分辨原發適應、原發不適應、次級、工具性情緒 | `emotion-differentiation`、`deepening` |
| 3 | `eft-focusing` | 標記：感受不清晰 → 任務：聚焦 | `marker-identification`、`focusing-guidance` |
| 4 | `eft-two-chair` | 標記：自我批評分裂 → 任務：雙椅對話 | `chair-setup`、`heightening` |
| 5 | `eft-empty-chair` | 標記：未完成事件 → 任務：空椅工作 | `evoking-the-other`、`need-expression` |
| 6 | `eft-transformation` | 標記：困惑的反應 → 系統性喚起展開；用情緒轉化情緒；EFT 的個案概念化 | `scene-rebuilding`、`meaning-bridge` |

- 椅子工作的練習題形式：個案在椅子對話中說了一句話，學生寫出治療師下一句的歷程引導。
- 每個模組的簡介要說明：這個任務在什麼標記出現時才用，以及什麼情況下不應該用。
- 繁中用語在動工時加入 `docs/plans/2026-11-15-zh-hant.md` 的用語表，先交擁有人確認譯名。

## 階段 6：DBT

### 範圍（擁有人已同意）

DBT 的首要治療目標是危及生命的行為。本系統的內容規則是「不示範風險處置流程」。兩者有衝突。

**建議的做法**：DBT 階段的貫穿個案，目標行為設定為不危及生命的行為（例如情緒爆發後的衝動行為、暴食、干擾治療的行為）。每個模組的簡介明確說明：危及生命行為的評估和處理流程不在本工具範圍內，要在督導下按機構守則學習。

擁有人已同意這個做法。日後擁有人要求納入危及生命行為的內容時，先停下來討論範圍和措辭，再寫任何內容。

### 模組

| # | slug | 重點 | 技能代碼 |
|---|---|---|---|
| 1 | `dbt-validation` | 生物社會理論；認可的層次 | `dbt-validation-levels`、`biosocial-explanation` |
| 2 | `dbt-commitment` | 承諾策略：利弊分析、得寸進尺與以退為進、魔鬼代言人、選擇的自由 | `commitment-eliciting`、`devils-advocate` |
| 3 | `dbt-chain` | 行為鏈分析 | `chain-questioning`、`link-identification` |
| 4 | `dbt-solutions` | 解決方案分析；技能教導與技能指導 | `solution-generation`、`skills-coaching` |
| 5 | `dbt-dialectics` | 辯證策略；在認可和改變之間取得平衡；溝通風格 | `dialectical-balance`、`irreverent-communication` |
| 6 | `dbt-tib` | 干擾治療的行為；與個案商議 | `tib-targeting`、`contingency-clarification` |

- 新的貫穿個案，先寫 `content/CLIENT_DBT.md` 交擁有人確認。
- 內容原創，不複製已出版的 DBT 手冊、講義和工作紙。技能名稱（例如四個技能模組的名稱）可以提及，但不重現其講義內容。
- 技能代碼 `dbt-validation-levels` 和基礎階段的 `validation` 是兩個不同的技能，譯名也要區分。

## 三個階段的次序

建議次序是 5（EFT）→ 6（DBT）→ 4（AI 回饋）。理由：EFT 和 DBT 只需要內容和「多階段支援」，不花錢，學生馬上受惠。AI 回饋要花錢，要先做一致性檢驗，而且階段 3 的報告功能完成後它才有完整用途。

擁有人可以改變次序。改之前把上面的理由告訴擁有人。
